# Local Development Setup

This is the actual, working way to run the platform locally. There is no deployment
manifest in this repo (see [00-architecture-overview.md](00-architecture-overview.md)'s
"Current deployment status") — this doc covers local dev only.

## Quick start

**All infrastructure runs locally in Docker — there is no cloud dependency for data.**
Postgres, Qdrant, and Redis are all containers defined in `infra/docker-compose.yml`.

From a clean checkout:

```bash
# 1. Start Postgres + Qdrant + Redis
docker compose -f infra/docker-compose.yml up -d

# 2. Create the schema
alembic upgrade head

# 3. Load demo data (both Postgres rows and Qdrant collections)
python scripts/seed_db.py
python scripts/seed_candidates_hardcoded.py    # richer candidate set, optional
```

If you have a Qdrant volume from before payload indexing existed, backfill the indexes
once (idempotent, safe to re-run — `seed_db.py` already does this for fresh volumes):

```bash
python scripts/ensure_qdrant_indexes.py
```

Without them, every filtered vector search — job matching's per-candidate project
relevance, deck plagiarism — scans the whole collection instead of just the matching
subset, so search time grows with total corpus size rather than result size.

Then start the app servers (or run `scripts/dev-up.ps1` on Windows to open all three in
separate PowerShell windows, launching Docker Desktop first if needed):

```bash
uvicorn services.api.main:app --reload --port 8000   # from the repo root
python -m services.workers.runner                    # background job worker
cd apps/web && npm run dev                           # http://localhost:3000
```

The **worker** consumes the Redis job queue that long AI pipelines are dispatched to —
candidate ingestion, job matching, assessment grading, pitch-deck analysis, and hackathon
ranking finalization.

Running it is optional. Before queueing, the API checks whether a worker is actually
alive (arq publishes a TTL'd health key) and runs the job in-process when none is — so
`uvicorn` on its own still works, it just loses durability across restarts and retries on
transient failures. Previously, Redis being up with no worker meant jobs were accepted
and then never executed: the row sat at `"processing"` forever with no error anywhere.
See §"Background job queue" below.

Seed logins are `alice@example.com` … `evan@example.com`, password `password123`.

> **Why everything is local:** running the database and vector store on loopback means
> a query costs what it costs to execute, with no network in the path. Hosting them
> elsewhere makes every query on every page pay a round trip before any application
> logic runs, which shows up as uniform slowness across the whole app and is invisible
> to a query profiler. See [guides/BACKEND_LATENCY_AUDIT.md](guides/BACKEND_LATENCY_AUDIT.md).

## Infrastructure

| Service | URL / location | Notes |
|---|---|---|
All three run as local Docker containers, started together by
`docker compose -f infra/docker-compose.yml up -d`. None of them require an account,
API key, or network access.

| Service | URL / location | Notes |
|---|---|---|
| Postgres | `localhost:5432` | `DATABASE_URL=postgresql+asyncpg://dev:dev@localhost:5432/talent_platform`, `DATABASE_SSL_REQUIRED=false`. Data persists in the `pgdata` Docker volume. |
| Qdrant | `localhost:6333` (REST), `6334` (gRPC) | `QDRANT_URL=http://localhost:6333`, `QDRANT_API_KEY` empty. Data persists in the `qdrantdata` volume. Dashboard at http://localhost:6333/dashboard. |
| Redis | `localhost:6379` | `REDIS_URL=redis://localhost:6379`. |

### Hosting the data tier elsewhere

Nothing in the code is local-only — only `.env` decides. Point `DATABASE_URL` /
`QDRANT_URL` / `QDRANT_API_KEY` at the hosted endpoints and set
`DATABASE_SSL_REQUIRED=true`, which also disables asyncpg's prepared-statement cache
for PgBouncer-style poolers. Expect materially higher per-query latency unless the app
is deployed in the same region as the database.

## Stopping everything

```bash
docker compose -f infra/docker-compose.yml stop      # keep data
docker compose -f infra/docker-compose.yml down      # remove containers, keep volumes
docker compose -f infra/docker-compose.yml down -v   # also wipe Postgres/Qdrant data
```

After `down -v` you must re-run `alembic upgrade head` and the seed scripts.

Close the two PowerShell windows opened by `dev-up.ps1` (or Ctrl+C in each) to stop the API
and web servers.

## Setting up secrets (`.env`)

Copy `.env.example` to `.env` and fill in the values below. Each integration is real and
currently used by the running app — none of these are placeholders for a feature that
doesn't exist.

**Postgres, Qdrant, and Redis need no secrets at all** — their defaults already point at
the local Docker containers. The only keys you must supply are for genuinely external
services (an LLM provider, and optionally GitHub OAuth / Cloudinary / Langfuse).

### 1. Anthropic API key

- **Variables**: `ANTHROPIC_API_KEY`
- **Purpose**: Access to Claude models (`claude-haiku-4-5-20251001` fast tier,
  `claude-sonnet-4-6` judgment tier) used across candidate scoring, matching, interviews,
  fraud narrative generation, and pitch deck rubric scoring.
- **How to get it**: [Anthropic Console](https://console.anthropic.com/) → API Keys → Create
  Key. Copy the key (starts with `sk-ant-api...`) into `ANTHROPIC_API_KEY`.

### 2. Database connection (PostgreSQL)

- **Variables**: `DATABASE_URL`, `DATABASE_SSL_REQUIRED`
- **Default (local Docker, no secrets required)**:
  `DATABASE_URL=postgresql+asyncpg://dev:dev@localhost:5432/talent_platform`,
  `DATABASE_SSL_REQUIRED=false`. Credentials are the throwaway `dev`/`dev` pair defined in
  `infra/docker-compose.yml`.
- **Hosted Postgres instead (optional)**: put the provider's connection string in
  SQLAlchemy/asyncpg form
  (`postgresql+asyncpg://<user>:<password>@<host>/<dbname>`) into `DATABASE_URL` and set
  `DATABASE_SSL_REQUIRED=true`. Expect materially higher per-query latency unless the app
  is deployed in the same region as the database.

### 3. Redis

- **Variable**: `REDIS_URL` (default `redis://localhost:6379`). Redis runs as a local
  Docker container in every setup, not a cloud service. No API key needed.
- **Used for**: the background job queue (arq). See below.

#### Background job queue

Long AI pipelines are dispatched to a Redis-backed [arq](https://arq-docs.helpmanual.io/)
queue and executed by `python -m services.workers.runner`, a process separate from the
API. Previously these ran as FastAPI `BackgroundTasks` inside the API process, which meant
they shared its event loop (one recruiter's matching run stalled every other request),
were lost silently on restart (rows stuck at `"processing"` with no way to retry), and
never retried a transient GitHub/LLM/Qdrant failure.

| Setting | Default | Purpose |
| --- | --- | --- |
| `QUEUE_ENABLED` | `true` | Set `false` to force the in-process fallback. |
| `QUEUE_JOB_TIMEOUT_SECONDS` | `900` | Per-job ceiling; must exceed the slowest pipeline. |
| `QUEUE_MAX_TRIES` | `3` | Total attempts, including the first. |
| `QUEUE_RETRY_BASE_DELAY_SECONDS` | `5` | Backoff base; doubles each attempt. |
| `QUEUE_RESULT_TTL_SECONDS` | `3600` | How long finished job results stay inspectable. |

Only *transient* failures are retried (timeouts, connection errors, rate limits, upstream
5xx). Permanent ones — bad input, a missing row, an unsupported file — are recorded on the
subject row immediately rather than burning the retry budget and delaying the user's error
message. Enqueues are idempotent per subject (`match:{job_id}`, `ingest:{profile_id}`, …),
so a double-clicked button coalesces into a single run.

Redis is also the store for the API rate limiter (`RATE_LIMIT_PER_MINUTE`), so the limit
holds across every API process instead of being multiplied by the worker count. If Redis
is unreachable the limiter degrades to a bounded per-process counter.

### 4. Qdrant vector database

- **Variables**: `QDRANT_URL`, `QDRANT_API_KEY`
- **Default (local Docker, no secrets required)**: `QDRANT_URL=http://localhost:6333`,
  `QDRANT_API_KEY=` (blank). Collections are created on demand by the app and by
  `scripts/seed_db.py`; browse them at http://localhost:6333/dashboard.
- **Hosted Qdrant instead (optional)**: set `QDRANT_URL` to the cluster endpoint and
  `QDRANT_API_KEY` to a cluster API key.

### 5. GitHub OAuth application

- **Variables**: `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GITHUB_OAUTH_REDIRECT_URI`
- **Purpose**: per-candidate GitHub authentication and profile/repository ingestion (the
  data source behind most Talent Score sub-scores).
- **How to get it**: [GitHub Developer Settings](https://github.com/settings/developers) →
  OAuth Apps → New OAuth App. Homepage URL `http://localhost:3000`, authorization callback
  URL `http://localhost:3000/api/auth/github/callback`. Copy the Client ID and generate a
  Client Secret into the corresponding variables.

### 6. Cloudinary file storage

- **Variables**: `CLOUDINARY_URL`, `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`,
  `CLOUDINARY_API_SECRET`
- **Purpose**: stores uploaded resumes, certificates, and profile media
  (`services/api/core/storage.py`, `services/api/integrations/storage/cloudinary_adapter.py`).
- **How to get it**: [Cloudinary Console](https://cloudinary.com/console) → Dashboard →
  Product Environment Credentials. Combine into
  `cloudinary://<API_KEY>:<API_SECRET>@<CLOUD_NAME>` for `CLOUDINARY_URL`.

### 7. Langfuse observability (optional)

- **Variables**: `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_HOST`
- **Purpose**: agent run tracing (`services/api/core/tracing.py`) — every `AgentRun` records
  a Langfuse trace ID when configured. Not required to run the app; empty keys mean a clean
  no-op, never a crash (same "typed empty default, fails closed" pattern used for the
  Anthropic and Cloudinary settings).
- **How to get it**: [Langfuse Cloud](https://cloud.langfuse.com/) → create a project →
  Settings → API Keys → Create new API Keys. Set `LANGFUSE_HOST=https://cloud.langfuse.com`
  (or your self-hosted URL).

### 8. Sentry error monitoring (optional)

- **Variable**: `SENTRY_DSN`
- **Purpose**: crash/exception reporting on API startup (`services/api/main.py`). An empty
  DSN means `sentry_sdk.init()` is never called at all — no partial state, just off.
- **How to get it**: [Sentry.io](https://sentry.io/) → Create Project (Python/FastAPI or
  Next.js) → Project Settings → Client Keys (DSN).

## Auth — no external secret required

Authentication is fully custom (email + password + JWT, see
[01-authentication-and-rbac.md](01-authentication-and-rbac.md)) — there is no third-party
identity provider to configure. The only auth-related settings are plain config values in
`services/api/core/config.py`:

| Setting | Default | Purpose |
|---|---|---|
| `jwt_secret_key` | *(required, no default)* | Signs and verifies access tokens |
| `jwt_algorithm` | `HS256` | JWT signing algorithm |
| `jwt_expiry_seconds` | `604800` (7 days) | Access token lifetime |

Set `JWT_SECRET_KEY` to any sufficiently random string in `.env` for local dev.
